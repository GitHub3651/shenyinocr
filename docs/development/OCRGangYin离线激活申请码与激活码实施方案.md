## 2. 终局结论

采用完全离线的双码流程：

```text
客户首次启动主程序
  -> 主程序按现有 S1 -> S2 策略生成本机设备标识
  -> 主程序显示“激活申请码”
  -> 客户把激活申请码发给供应商
  -> 供应商在 LicenseTool 中选择有效期、授权模式、默认模式和有效期显示授权
  -> LicenseTool 根据授权信息生成“激活码”
  -> 客户在主程序中粘贴激活码
  -> 主程序解码并验证设备、有效期和模式
  -> 验证成功后生成加密字段格式的 version=5 license.ini
  -> 继续启动主界面
```

固定使用以下名称：

- **激活申请码**：客户机器生成并发给供应商的代码。
- **激活码**：供应商根据激活申请码和授权配置签发、再发回客户的代码。
- **许可证**：主程序验证激活码后保存的 `version=5` 文本文件。

## 3. 许可证终局数据模型

许可证固定为七行 `version=5` UTF-8 文本文件。激活码运输设备摘要、有效期、授权模式、默认模式和有效期显示授权；主程序验证激活码后，使用本机完整设备码生成许可证。

### 3.1 授权数据

| 逻辑数据 | 逻辑值 |
|---|---|
| 格式版本 | `version=5`，保持明文 |
| 有效期 | `expires=yyyy-MM-dd` 或 `expires=permanent` |
| 授权模式 | `features=<modeId 列表>` |
| 默认模式 | `defaultMode=<modeId>` |
| 设备绑定方式 | `deviceBinding=S1` 或 `deviceBinding=S2` |
| 设备码 | `deviceCode=<64位大写十六进制设备码>` |
| 显示有效期 | `showExpiry=true` 或 `showExpiry=false` |

### 3.2 唯一格式约束

- 许可证第一行固定为明文 `version=5`，随后固定包含 `expires`、`features`、`defaultMode`、`deviceBinding`、`deviceCode` 和 `showExpiry` 六个加密键值字段。
- 六个字段的字段名和值分别加密并写成大写十六进制文本。
- 许可证不包含激活状态字段或激活状态值。
- 主程序读取 LicenseTool 已经确定的授权内容，并使用本机完整设备码生成许可证。
- 首次启动没有许可证时直接显示激活界面和激活申请码。
- 激活申请码固定为 16 位纯数字，激活码固定为 24 位纯数字；主程序和 LicenseTool 中的申请码、激活码均每 4 位使用空格分组。
- 客户名称、订单号、签发日期、激活日期和许可证编号不属于许可证数据。

## 4. 许可证字段与数字码加密方式

### 4.1 许可证字段固定算法

- 固定密钥沿用当前许可证实现使用的密钥常量。
- 使用 SHA-256 对固定密钥求摘要，得到 32 字节异或密钥。
- 字段名和值分别转换为 UTF-8 字节，再与异或密钥循环异或。
- 异或结果转换为大写十六进制文本后写入文件。
- 解密时按相反顺序执行：十六进制解码、循环异或、UTF-8 解码。
- 相同字段或相同值每次生成相同密文，不增加随机数、IV 或其他加密参数。

实现继续使用 QtCore 的 `QCryptographicHash` 和现有异或逻辑，不增加第三方库、Windows 加密 API 或新的加密组件。

### 4.2 许可证字段数据边界

许可证字段加密内容只包含有效期、授权模式、默认模式、设备绑定方式、设备码和有效期显示授权。文件解析后完成日期、S1/S2 和当前设备码校验；无法解密或无法按固定格式解析时许可证无效。

### 4.3 数字码加密与输入校验

激活申请码和激活码的数字主体使用现有固定密钥派生数字密钥流：

1. 对现有固定密钥求 SHA-256，得到基础密钥。
2. 激活申请码使用 ASCII 标签 `REQ4-NUMERIC`，激活码使用 ASCII 标签 `ACT4-NUMERIC`；分别计算 `SHA256(基础密钥字节 + 标签字节)`，得到两组不同的密钥流。
3. 依次将密钥流字节对 10 取余，得到每一位使用的数字密钥。
4. 加密时执行 `密文数字 = (明文数字 + 密钥数字) % 10`。
5. 解密时执行 `明文数字 = (密文数字 - 密钥数字 + 10) % 10`。

类型前缀和最后一位 Luhn 校验位不加密。生成时对“类型前缀 + 加密主体”计算标准 Luhn 校验位并追加到末尾；解析时先校验完整数字码，校验失败时不继续解密。数字码不包含 HMAC、数字签名、随机数或其他字段。

## 5. 激活申请码格式

主程序先按现有规则取得设备标识：

1. 优先读取并规范化 `Win32_ComputerSystemProduct.UUID`，有效时使用 S1。
2. S1 无效时读取并规范化 `Win32_BaseBoard.SerialNumber` 与 `Win32_BIOS.SerialNumber`，两者都有效时使用 S2。
3. S1 设备码为 `SHA256(NormalizedSystemUUID)`。
4. S2 设备码为 `SHA256(NormalizedBaseboardSerial + "|" + NormalizedBiosSerial)`。
5. 规范化、占位值排除和 S1/S2 不自动切换规则保持现状，不增加 MachineGuid、MAC 地址、磁盘序列号或其他来源。

内部设备标识固定为：

```text
S1:<64位大写十六进制设备码>
```

或：

```text
S2:<64位大写十六进制设备码>
```

主程序根据绑定方式和完整设备码生成设备摘要：

1. 计算 `SHA256(绑定方式 + "|" + 完整设备码)`。
2. 将摘要前 5 字节按大端无符号整数读取并右移 1 位，取得摘要最前面的 39 bit，再转换为十进制。
3. 左侧补零，固定为 12 位设备摘要。

绑定方式编码固定为 `1=S1`、`2=S2`。激活申请码的 13 位明文主体为：

```text
1位绑定方式 + 12位设备摘要
```

按第 4.3 节加密后，激活申请码固定为：

```text
41 + 13位加密主体 + 1位Luhn校验位
```

激活申请码总长 16 位纯数字，显示示例为 `4112 3456 7890 1238`；空格只用于分组，解析时去除。激活申请码不包含完整设备码、有效期、授权模式、客户资料或时间戳。同一设备在硬件标识不变时生成同一个激活申请码。

激活申请码只向 LicenseTool 传递绑定方式和设备摘要。完整设备码始终保留在客户电脑中。

## 6. 激活码与 license.ini 格式

### 6.1 固定 license.ini 内容

`license.ini` 使用 UTF-8 文本，第一行保持明文，其余字段名和值使用第 4.1 节的现有加密方式。字段顺序固定且只允许以下七行：

```text
version=5
Encrypt("expires")=Encrypt("yyyy-MM-dd" 或 "permanent")
Encrypt("features")=Encrypt("stamp,word,ocr,tissue,barcodeWord" 中的一个或多个)
Encrypt("defaultMode")=Encrypt(features 中的一个 modeId)
Encrypt("deviceBinding")=Encrypt("S1" 或 "S2")
Encrypt("deviceCode")=Encrypt(64位大写十六进制设备码)
Encrypt("showExpiry")=Encrypt("true" 或 "false")
```

规则如下：

- `version` 必须等于 `5`。
- `deviceBinding` 必须来自激活码，`deviceCode` 必须使用主程序当前取得的完整设备码，两者均不允许手工编辑。
- `expires` 只使用一个字段表达具体日期或长期有效。
- `features` 至少包含一个现有稳定 `modeId`。
- `features` 按 `detectionModeDescriptors()` 的顺序写入，使用英文逗号且不带空格。
- `defaultMode` 必须属于 `features`。
- `showExpiry` 只允许 `true` 或 `false`。
- 文件可以在最后一行后带一个换行，不允许额外字段、字段别名、缺省字段或不同字段顺序。

### 6.2 激活码

`LicenseTool` 从激活申请码取得绑定方式和 12 位设备摘要，再与授权配置组成 21 位明文主体：

| 字段 | 长度 | 编码 |
|---|---:|---|
| 设备绑定方式 | 1 位 | `1=S1`、`2=S2` |
| 设备摘要 | 12 位 | 来自激活申请码 |
| 有效期 | 5 位 | `00000` 表示长期有效；具体日期为从 `2020-01-01` 起的天数加一，左侧补零 |
| 授权字段 | 2 位 | 两位十进制数 `01`～`63` |
| 默认模式 | 1 位 | `1`～`5`，顺序与授权模式一致 |

授权字段按二进制位固定为：

| 位 | 数值 | 含义 |
|---:|---:|---|
| 0 | 1 | `stamp` |
| 1 | 2 | `word` |
| 2 | 4 | `ocr` |
| 3 | 8 | `tissue` |
| 4 | 16 | `barcodeWord` |
| 5 | 32 | 在软件设置中显示许可证有效期 |

低五位至少包含一个授权模式；默认模式按同一顺序编码为 `1`～`5`，并且必须属于授权模式。具体日期编码必须在 `00001`～`99999` 范围内。

21 位明文主体按第 4.3 节加密后，激活码固定为：

```text
42 + 21位加密主体 + 1位Luhn校验位
```

激活码总长 24 位纯数字，显示示例为 `4212 3456 7890 1234 5678 9012`；空格只用于分组，解析时去除。

### 6.3 license.ini

主程序解析激活码，验证 Luhn 校验位、绑定方式、本机设备摘要和有效期，并读取 LicenseTool 已经确定的授权模式、默认模式和有效期显示授权。全部通过后，以激活码中的授权数据、本机绑定方式和本机完整设备码构造 `LicenseData`，再按第 4.1 节生成规范化的七行文本，并使用 `QSaveFile` 写入应用程序目录下的 `license.ini`。写入前不创建占位文件。

## 7. 主程序首次运行与后续启动

### 7.1 启动检查

`RuntimeGuard::check()` 仍是唯一启动许可证入口：

1. 尝试读取 `<exe>/license.ini`。
2. 文件存在时，验证明文 `version=5`，解密六个固定键值字段。
3. 按 `deviceBinding` 中的 S1 或 S2 重新计算当前设备码，并与 `deviceCode` 完全比较。
4. 校验有效期。
5. 全部通过时返回现有启动层需要的有效期、有效期显示授权、授权模式和默认模式，继续启动。
6. 文件缺失、格式或解密无效、已过期或设备不匹配时，为当前设备生成激活申请码并进入激活界面，同时显示对应的具体原因。
7. 许可证文件存在但无法读取时，提示许可证读取失败并退出，不把读取失败当作未激活。
8. 当前机器无法按 S1 或 S2 生成有效设备标识时，提示无法获取本机设备信息并退出。

### 7.2 激活界面

新增单一 `ActivationDialog`，在主窗口组装之前显示。界面只包含：

- 当前状态提示，用于显示未激活、许可证到期、许可证无效或设备不匹配的具体原因。
- 说明文字：“请将激活申请码发送给供应商，获取激活码后粘贴到下方。”
- 只读激活申请码文本框。
- “复制申请码”按钮。
- 激活码输入框。
- “激活”按钮。
- “退出”按钮。

不增加客户名称、联系方式、试用申请、联网按钮、文件导入、二维码、历史记录或许可证详情页。

“复制申请码”成功写入剪贴板后，使用统一消息框提示“激活申请码复制成功。”。复制和退出按钮继承普通按钮的默认、焦点、悬停、按下和禁用状态；激活按钮使用现有 `uiRole=primary` 的对应完整状态，不在对话框内设置局部样式。

激活码输入框不使用输入掩码，只接受最多 24 位数字；输入和粘贴时忽略非数字字符，并在每 4 位数字之间自动显示一个空格。用户可以在中间选择数字后直接修改，格式化后光标保持在对应的数字位置。

用户点击“激活”后：

1. 去除分组空格。
2. 验证输入是 24 位纯数字、前缀为 `42` 且 Luhn 校验通过。
3. 解密并解析 21 位主体。
4. 验证激活码中的绑定方式等于当前设备，并验证设备摘要等于根据本机完整设备码重新生成的摘要。
5. 验证有效期并读取授权模式、默认模式和有效期显示授权。
6. 使用本机完整设备码构造七行 `version=5` 许可证，并通过 `QSaveFile` 写入 `license.ini`。
7. 直接把激活结果交回启动层并继续启动，不要求重新启动程序，也不再次读取文件。

激活提交失败时按本节“固定状态与提示文案”显示对应原因。提示只说明客户可以采取的动作，不显示加密密钥、设备原始值、解密细节或内部错误码。

### 7.3 后续启动与续期

- 后续启动读取同一个 `license.ini`，验证通过后不显示激活界面。
- 许可证到期、损坏或被复制到另一台设备时，显示当前设备的激活申请码，可重新获取激活码并覆盖 `license.ini`。
- 具体日期许可证继续使用启动阶段确认的到期日期创建 24 小时定时器；运行期间发现到期时提示“软件许可证到期，请重新激活。”，确认后退出，下一次启动进入激活界面。
- `permanent` 不创建到期定时器。
- 不检查系统时钟回拨，不增加在线校时或本地时间历史文件。

### 7.4 固定状态与提示文案

启动检查、激活提交和运行期间到期使用同一组事实状态，但根据用户当前操作显示“许可证”或“激活码”文案。不传递任意错误字符串，不建立错误码框架。

#### 已保存许可证的启动提示

| 原因 | 固定提示 | 后续行为 |
|---|---|---|
| `license.ini` 不存在 | “软件尚未激活，请输入激活码。” | 显示激活界面和当前设备的激活申请码 |
| 格式错误或解密失败 | “软件许可证无效，请重新激活。” | 显示激活界面和当前设备的激活申请码 |
| 已超过到期日期 | “软件许可证到期，请重新激活。” | 显示激活界面和当前设备的激活申请码 |
| 与当前设备不匹配 | “软件许可证与当前设备不匹配，请重新激活。” | 显示激活界面和当前设备的激活申请码 |
| 文件存在但无法读取 | “软件许可证读取失败，请检查软件目录权限。” | 使用模态提示，确认后退出 |
| 无法生成 S1 或 S2 设备标识 | “无法获取本机设备信息，请联系供应商。” | 使用模态提示，确认后退出 |

#### 用户提交激活码的提示

| 原因 | 固定提示 | 后续行为 |
|---|---|---|
| 输入为空 | “请输入激活码。” | 停留在激活界面 |
| 长度、字符、前缀、Luhn 校验、格式或解密无效 | “激活码无效，请确认后重试。” | 停留在激活界面 |

| `license.ini` 保存失败 | “许可证保存失败，请确认软件目录可写。” | 停留在激活界面，不进入主界面 |

#### LicenseTool 输入提示

| 原因 | 固定提示 |
|---|---|
| 激活申请码为空 | “请输入激活申请码。” |
| 激活申请码长度、字符、前缀、Luhn 校验或解密后的绑定方式无效 | “申请码无效，请确认输入是否正确。” |
| 未选择授权模式 | “请至少选择一个授权模式。” |

同一原因只显示一次：进入激活界面的原因放在对话框状态提示中，不先弹出消息框再打开对话框；只有无法继续激活的许可证读取失败和设备标识获取失败使用退出消息框。

## 8. LicenseTool 终局界面与流程

`LicenseTool` 负责根据激活申请码和授权配置签发激活码，并读取现行 24 位激活码和 `version=5` `license.ini` 的授权内容。

界面固定为四个区域：

### 8.1 激活申请

- 激活申请码输入框。
- 只读识别状态，成功时只显示“申请码有效，绑定方式：S1”或“S2”。

不提供设备标识手工输入框。点击“生成激活码”时，先去除分组空格，再依次验证 16 位纯数字、`41` 前缀和 Luhn 校验；任一失败均显示“申请码无效，请确认输入是否正确。”，且不继续解密或生成激活码。校验通过后解密得到绑定方式和 12 位设备摘要，绑定方式只接受 S1/S2 对应值；LicenseTool 不持有完整设备码，不对设备摘要增加外部查询或第二套校验。

### 8.2 授权配置

- 有效期类型：具体日期或长期有效。
- 具体到期日期；最小值为当天，最大值为 5 位日期编码能够表示的 `2293-10-14`。
- 五种检测模式多选。
- 默认模式下拉框，只显示当前已选择的授权模式。
- “在软件设置中显示许可证有效期”复选框，默认勾选。

模式名称、稳定 ID 和顺序继续唯一来自 `detectionModeDescriptors()`。

### 8.3 激活码输出

- “生成激活码”按钮。
- 只读激活码文本框。
- “复制激活码”按钮。
- 状态提示。

生成时只校验申请码有效且至少选择一个授权模式。默认模式始终由只包含已选授权模式的下拉框给出，具体日期由日期控件范围限制。生成成功后将绑定方式、设备摘要、有效期、授权模式、默认模式和有效期显示授权编码为 24 位纯数字激活码并显示，不生成中间文件或许可证文件。

“复制激活码”成功写入剪贴板后，使用消息框提示“激活码复制成功。”。

### 8.4 授权内容读取

- 输入现行 24 位激活码并读取设备绑定方式、12 位设备摘要、有效期、授权模式、默认模式和有效期显示授权。
- 选择现行 `version=5` `license.ini`，解密并读取设备绑定方式、完整设备码、有效期、授权模式、默认模式和有效期显示授权。
- 两类内容显示在同一个只读结果框中；无效或无法读取时只显示固定失败提示。

工具最终界面只包含上述激活申请、授权配置、激活码输出和授权内容读取四个区域。

## 9. 代码职责与接口终局

### 9.1 LicenseCodec

`LicenseCodec` 只承担以下职责：

- 计算本机设备摘要并生成激活申请码。
- 解析供应商签发的激活码。
- `version=5` 许可证固定字段的加密、解密和结构解析。
- 读取 `license.ini`，并通过 `QSaveFile` 保存上层已经组装和验证完成的 `LicenseData`。

读取结果只区分文件不存在、文件读取失败、许可证无效和成功；无法解密或无法按固定格式解析统一属于许可证无效，不继续细分数字码内部步骤、字段行数或日期解析步骤。

`LicenseData` 只保留运行需要的数据：

- `deviceBinding`：`S1` 或 `S2`。
- `deviceCode`：64 位大写十六进制设备码。
- `permanent` 与 `expiresDate`。
- `showExpiry`。
- `featureModeIds`。
- `defaultModeId`。

序列化时 `deviceBinding` 和 `deviceCode` 分别写入对应字段，内存结构继续保持两个直接字段。

`LicenseCodec` 继续使用现有 `secretKey()`、`cryptData()`、`encryptText()` 和 `decryptText()` 完成字段名和值的加解密。`writeFile()` 接收完整 `LicenseData`，固定写入真实的 S1/S2、设备码和有效期显示授权。

### 9.2 RuntimeGuard

`RuntimeGuard` 保留现有 WMI 读取、规范化和设备码计算，实现以下两个直接入口：

- 启动检查：读取并验证已有许可证；无有效许可证时返回当前设备的激活申请码。
- 激活提交：验证用户输入的激活码、保存并返回本次启动授权结果。

`RuntimeGuardResult` 用一个状态枚举直接区分：

- `Valid`：有效许可证，可以继续启动；
- `LicenseMissing`：许可证不存在，需要激活；
- `LicenseInvalid`：格式无效或解密失败，需要重新激活；
- `LicenseExpired`：许可证到期，需要重新激活；
- `DeviceMismatch`：许可证不属于当前设备，需要重新激活；
- `LicenseReadFailed`：许可证文件无法读取，阻止启动；
- `DeviceUnavailable`：无法取得设备标识，阻止启动；
- `LicenseSaveFailed`：激活码验证通过但许可证保存失败，停留在激活界面。

需要激活的状态同时携带当前设备的激活申请码；`Valid` 同时携带有效期、有效期显示授权、授权模式和默认模式。状态枚举是界面提示的唯一映射依据。

不建立授权服务、仓储层、策略接口、全局单例或第二套设备标识实现。

### 9.3 ApplicationStartup

`ApplicationStartup` 在读取 `AppSettings` 之前完成许可证检查。需要激活时把具体状态交给 `ActivationDialog` 显示第 7.4 节规定的原因；许可证读取失败或设备标识不可用时显示固定退出提示；激活成功后继续使用同一个已验证结果组装现有服务和主窗口。

### 9.4 许可证成功后的现有行为

许可证读取或本次激活成功后，向现有启动调用链提供 `permanent`、`expiresDate`、`showExpiry`、`authorizedModeIds` 和 `defaultModeId`，并保持以下行为：

1. `authorizedModeIds` 按 `detectionModeDescriptors()` 的固定顺序，从许可证 `features` 中生成；`defaultModeId` 直接使用许可证 `defaultMode`。
2. 许可证 `defaultModeId` 是主程序启动默认模式的唯一来源。`AppSettings` 只保存当前选中的检测模式，不再提供固定的检测模式默认值，也不以字库匹配或任一模式作为兜底。
3. `ApplicationStartup` 仍在许可证成功后读取 `AppSettings`。首次运行、设置文件按现有规则重建、清空软件数据后的下一次启动，或者已保存模式不在 `authorizedModeIds` 中时，使用许可证 `defaultModeId`；已保存模式仍获授权时继续使用已保存模式。
4. 设置文件需要重建时，先把许可证 `defaultModeId` 对应的 UI ID 写入新建的 `AppSettings`，再通过现有 `AppSettingsStore::save()` 保存，不能先保存主程序内置模式。
5. 模式选择只改变当前使用的 `detectModeId`，不删除、不清空也不改写其他模式的设置、模板、模型或识别资源。
6. `ApplicationStartup` 继续把完整 `authorizedModeIds` 传给 `MainWindow`，再由 `MainWindow` 原样传给 `MachineSettingsPage`。
7. `MachineSettingsPage` 继续按 `detectionModeDescriptors()` 的顺序，只向检测模式下拉框加入已授权模式；模式切换、模板恢复和各模式参数界面继续使用下拉框中的实际模式数据。
8. 软件设置页继续只显示已授权模式对应且文件实际存在的使用说明书链接；没有可显示说明书时隐藏说明书区域。字符识别模式使用 `晟崟AI视觉检测软件使用说明书.pdf`，其他模式说明书文件名、`<exe>/document` 路径和打开方式均不变。
9. 具体日期许可证继续使用启动阶段取得的 `expiresDate` 创建 24 小时定时器；`permanent` 不创建该定时器。定时器不重新读取许可证，也不重新处理授权模式。
10. “清空当前软件数据”继续只删除当前 Windows 用户的 `app_settings.json`，不删除 `license.ini`、模板、识别图片或日志；下一次启动按许可证 `defaultModeId` 初始化检测模式。
11. 软件设置页根据 `showExpiry` 显示具体日期或“长期有效”；未授权显示时隐藏整行，且不提供修改入口。
12. 许可证字段和完整设备码继续只由许可证与启动边界持有，不写入 `AppSettings`、模板或日志。

除许可证有效期只读呈现外，不修改 `MachineSettingsPage`、`TemplateEditorPage`、设置 Schema、模板 Schema、模式切换、模板恢复、说明书筛选与打开逻辑或清空软件数据逻辑。其他设置默认值及设置文件格式不变。

### 9.5 LicenseTool 边界

`LicenseTool` 在自身目录的 `activation_protocol.h/.cpp` 中解析 16 位申请码、根据授权配置生成 24 位激活码，并只读解析现行 24 位激活码和 `version=5` `license.ini`。工具不编译或包含 `app/` 下的源码，不通过申请码或激活码取得完整设备码、不构造主程序 `LicenseData`、不生成或修改 `license.ini`。完整设备码只在用户主动读取现有许可证文件时显示。主程序只生成申请码、解析激活码并使用本机完整设备码生成许可证；主程序界面和启动流程不提供生成激活码的操作入口。

### 9.6 协议同步维护约束

主程序与 `LicenseTool` 虽然不共享源码，但固定密钥、类型前缀、密钥流标签、数字加解密、Luhn 校验、字段位置和长度、日期基准、S1/S2 编码、授权模式 ID、位图顺序、有效期显示位及默认模式编号共同构成唯一激活协议。修改其中任何一项时，必须同步修改 `app/system_support/license/license_codec.cpp` 和 `tools/license_tool/activation_protocol.cpp`，并重新验证“主程序生成申请码 → LicenseTool 签发激活码 → 主程序解析并完成激活”的完整闭环。

两端任一协议项不一致时，必须直接统一字段定义和协议实现，并重新完成闭环验证。

## 11. 实施阶段

### 阶段 A：许可证格式与字段加密

1. 定义七行 `version=5` 许可证、16 位申请码、24 位激活码、设备摘要和 Luhn 规则。
2. 许可证字段沿用现有固定密钥、SHA-256 密钥派生、循环异或和大写十六进制编码；数字码主体使用同一固定密钥派生的十进制密钥流。
3. `LicenseCodec` 提供主程序使用的申请码生成、激活码解析和 `version=5` 许可证读写入口。
4. 许可证写入真实设备绑定信息和有效期显示授权。

### 阶段 B：LicenseTool 签发与读取流程

1. 将激活申请码作为唯一设备输入。
2. 在工具自身的 `activation_protocol.h/.cpp` 中校验申请码长度、纯数字格式、`41` 前缀和 Luhn 校验位，解密取得绑定方式和设备摘要。
3. 配置有效期、授权模式、默认模式和有效期显示授权，生成 24 位纯数字激活码并提供复制按钮。
4. 保留现行激活码与 `version=5` 许可证的只读查看功能。
5. `LicenseTool.pro` 只编译工具目录内文件，不包含或编译 `app/` 源码。

### 阶段 C：主程序激活流程

1. `RuntimeGuard` 用单一状态枚举返回许可证不存在、无效、到期、设备不匹配、读取失败和设备信息不可用。
2. 在需要激活的状态下生成 16 位纯数字申请码，并新增单一激活对话框显示对应原因。
3. 验证用户输入的 24 位激活码，以本机完整设备码核对设备摘要；成功后使用本机完整设备码写入七行 `version=5` `license.ini` 并继续启动。
4. 成功结果向启动层返回有效期、有效期显示授权、按固定顺序排列的授权模式集合和许可证默认模式。
5. 主窗口按显示授权在软件设置页显示具体日期、“长期有效”或隐藏整行。
6. 运行期间到期时提示“软件许可证到期，请重新激活。”。

### 阶段 D：发布与净删除

1. 发布包不再携带预制 `license.ini`。
2. 部署脚本不再复制或要求 `license.ini`。
3. 删除旧许可证格式、旧工具控件、旧声明、旧调用和旧工程条目。
4. 更新现行说明和功能证据，不保留兼容入口。

## 12. 验收清单

### 12.1 激活申请码

- 无 `license.ini` 首次启动时显示激活界面和 16 位纯数字申请码。
- 点击“复制申请码”后剪贴板内容等于当前显示的申请码，并提示“激活申请码复制成功。”。
- 同一设备重复启动生成相同申请码。
- 申请码前缀固定为 `41`，最后一位 Luhn 校验有效，显示时每 4 位分组。
- 申请码只包含加密后的绑定方式和 12 位设备摘要，不包含完整设备码。
- S1 有效时使用 S1；S1 无效且 S2 完整时使用 S2。
- 无法生成 S1/S2 时阻止启动，不创建空许可证。

### 12.2 LicenseTool

- 有效申请码可以配置具体日期或长期有效、多个模式和默认模式。
- 有效期显示复选框默认勾选，可生成显示或隐藏有效期的激活码。
- 申请码不是 16 位纯数字、前缀不是 `41`、Luhn 校验失败或解密内容无效时不生成激活码，并提示“申请码无效，请确认输入是否正确。”。
- 生成结果为 24 位纯数字激活码，前缀固定为 `42`，最后一位 Luhn 校验有效，显示时每 4 位分组。
- 默认模式只能来自已授权模式。
- 工具可只读查看现行激活码和 `version=5` `license.ini`，不生成或修改许可证文件。
- 申请码为空或无效、未选择模式时，分别显示第 7.4 节规定的固定提示；具体日期控件不能选择当天以前或 `2293-10-14` 以后的日期。

### 12.3 主程序激活

- 本机有效激活码可以保存并立即进入主界面，无需重启。
- 重启后直接读取 `license.ini` 并正常启动。
- 激活码不是 24 位纯数字、前缀不是 `42`、Luhn 校验失败或无法解密时不能激活。
- 另一台设备的激活码不能激活本机。
- 过期激活码不能激活；长期有效激活码不创建到期定时器。
- 保存失败时不进入主界面，不保留半写入文件。
- 激活成功后生成的 `license.ini` 第一行为明文 `version=5`，其余六行分别保存加密后的有效期、授权模式、默认模式、设备绑定方式、设备码和有效期显示授权。
- 许可证不存在、无效、到期和设备不匹配时，激活界面分别显示第 7.4 节规定的具体原因。
- 输入为空、激活码无效、激活码到期、设备不匹配和保存失败时，分别显示第 7.4 节规定的固定提示。
- 激活码输入框不显示掩码占位符，只保留最多 24 位数字并每 4 位自动使用空格分组；中间修改后光标保持在对应数字位置。
- 激活窗口继承唯一正式 QSS；顶部状态提示以危险红色和 600 加重显示；复制和退出按钮具备普通按钮完整状态，激活按钮具备主操作按钮的默认、焦点、悬停、按下和禁用状态，按钮获得焦点后仍能显示悬停和按下效果，界面和 C++ 中不存在局部 `styleSheet`。
- 许可证读取失败或无法生成设备标识时显示对应具体原因并退出，不打开无法完成的激活流程。
- 运行期间许可证到期时提示“软件许可证到期，请重新激活。”。

### 12.4 授权行为

- 许可证读取或激活成功后，状态为 `Valid` 的 `RuntimeGuardResult` 携带正确的 `permanent`、`expiresDate`、`showExpiry`、`authorizedModeIds` 和 `defaultModeId`。
- `authorizedModeIds` 按 `detectionModeDescriptors()` 的固定顺序生成，不按许可证文本顺序或数字位图另建顺序。
- 首次启动、设置文件按现有规则重建以及清空软件数据后的下一次启动，均使用许可证中的 `defaultMode`。
- 已保存且已授权的模式继续恢复。
- 已保存模式未授权时使用 `defaultMode`，其他设置和模板不删除。
- 主程序不存在固定的检测模式默认值，设置创建和序列化也不以字库匹配或其他模式兜底。
- 设置页只显示激活码 `features` 中的模式，顺序来自 `detectionModeDescriptors()`。
- 软件设置页只显示已授权模式对应且文件存在的说明书链接；未授权模式的说明书不显示，说明书区域无内容时隐藏。
- 授权模式切换继续驱动现有模式参数界面、模板恢复和检测准备，不增加第二套模式状态。
- “清空当前软件数据”继续保留 `license.ini`、模板、识别图片和日志。
- 许可证字段和完整设备码不进入 `AppSettings`、模板、日志或主界面。
- 具体日期许可证启动 24 小时到期定时器，行为与当前合同一致。
- 软件设置页根据 `showExpiry` 显示具体日期或“长期有效”；未授权显示时隐藏整行。

### 12.5 发布与静态门禁

- 客户发布包不包含 `LicenseTool` 或预制 `license.ini`。
- Release 部署除停止携带预制 `license.ini` 外，其他运行资源和说明书部署行为保持不变。
- `UNACTIVATED`、`version=3` 和旧许可证文件生成/读取控件在生产代码中零引用。
- 生产代码只存在七行 `version=5` 许可证解析路径。
- `LicenseTool.pro` 不包含 `APP_ROOT`、`../../app` 或任何 `app/` 源文件，主程序也不保留申请码解析和激活码生成接口。
- 许可证加解密只使用现有 QtCore 实现，不增加其他加密依赖。
- UI XML、qmake 文件、UTF-8、工程文件清单和 `git diff --check` 通过。
- 主程序和 `LicenseTool` 由用户在 Qt Creator 中分别完成构建与人工验证。

## 13. 明确不做

- 不建设在线授权服务器、账号系统、后台管理页面或数据库。
- 不增加网络请求、在线校时、远程吊销或激活次数统计。
- 不增加试用期、宽限期、离线计数器或系统时钟回拨检测。
- 不增加 TPM、加密狗、MAC 地址、MachineGuid 或磁盘序列号。
- 不增加客户名称、订单号、签发日期、激活日期或许可证编号。
- 不给 LicenseTool 增加密码登录、权限系统、密钥管理页面或多密钥框架。
- 不给数字码增加 HMAC、数字签名、随机数或第二套加密组件。
- 不保留旧许可证读取、旧许可证生成、旧首次自绑定或新旧格式转换路径。
- 不修改检测算法、模式 ID、模板 Schema、设置 Schema、相机、PLC、存图、统计或日志合同。

## 14. 实施完成后的唯一状态

- 客户第一次运行得到激活申请码。
- 供应商通过内部 `LicenseTool` 生成激活码，并可只读查看现行激活码和 `version=5` 许可证内容。
- 激活申请码为 16 位纯数字，激活码为 24 位纯数字，二者均包含类型前缀、加密主体和一位 Luhn 校验位。
- LicenseTool 从申请码和激活码中取得绑定方式、设备摘要和授权内容；读取用户主动选择的 `license.ini` 时可显示其中的完整设备码。客户输入激活码后，主程序使用本机完整设备码生成七行 `version=5` `license.ini`。
- 许可证是主程序启动默认模式的唯一来源；已保存且仍获授权的模式继续恢复，首次运行、设置重建或已保存模式未获授权时使用许可证默认模式。
- 许可证成功后的授权模式输出、模式下拉框、说明书展示、模板和设置保留及到期定时器继续使用现有调用链和现有行为。
- 主程序界面只验证和保存，不提供激活码生成功能。
- LicenseTool 与主程序不共享源码，双方只通过固定格式的申请码和激活码交换数据。
- 主程序仅在许可证解密成功、当前设备匹配且有效期有效时放行启动。
- 软件设置页按照许可证中的 `showExpiry` 显示或隐藏许可证有效期。
- 仓库生产代码只保留 16 位申请码、24 位激活码和七行 `version=5` `license.ini` 一套格式。
