## 给 Agent 的执行指令

你现在要正式执行 OCRGangYin Qt/C++ 工业视觉软件的架构重构，不是继续讨论、重新设计或反复审查计划书。

### 1. 必读依据和优先级

首先完整读取并使用 `$ocrgangyin-refactor` Skill，然后完整读取：

1. `docs/development/OCRGangYin工业视觉框架升级计划.md`
2. `docs/development/OCRGangYin现有功能对照表.md`（若不存在，阶段0负责创建）
3. `docs/development/OCRGangYin重构执行记录.md`（若不存在，阶段0负责创建）
4. 当前 `app/` 源码、Qt工程文件、UI文件、资源文件、脚本和实际调用链

`docs/development/提示词.md` 是早期多相机和安全校验任务记录，不是本次架构重构的执行依据，不要按它启动多相机开发。

执行依据的含义如下：

- 当前 `app/` 是已有功能、参数来源、交互行为、线程行为和硬件副作用的事实来源。
- 升级计划规定目标架构、阶段顺序、已确认优化和范围边界。
- Skill规定每个阶段和切片的执行方法与门禁。
- 若三者存在不能自行消解的冲突，先通过源码和可重复操作确认事实；只有会改变用户可观察结果、检测判定或硬件行为时才询问用户。

### 2. 总体目标

以“拆解现有代码并重组”为主，不脱离旧实现重新开发一套软件。把 `app/` 中已经存在的职责逐步迁入计划规定的：

```text
startup/
ui/
recipes/
detection/
devices/
runtime/
system_support/
```

最终提高可读性、可维护性和新增检测功能的便利性，同时保证现有可达功能都有明确去向和回归证据。

### 3. 本次授权范围

你已获得以下授权：

- 在本仓库内读取、修改、新增和移动本次重构需要的源码、测试、Qt工程清单和开发文档。
- 执行必要的只读盘点、轻量静态检查和代码审查；可以编写测试源码，但不得自行编译或运行Qt/C++目标。
- 按本文件的Git规则创建或沿用 `codex/` 前缀的重构分支，并创建本地提交。
- 阶段0门禁通过后自动进入阶段1；阶段1通过后进入阶段2；阶段2通过后进入阶段3。普通分析和文档切片不需要等待用户回复，代码切片必须遵守下一节的Qt Creator构建门禁。

授权到阶段3结束为止。不得自动进入阶段4，不得擅自推送远程仓库、创建PR、改写Git历史或发布软件。

### 4. 构建职责边界（最高优先级）

本项目必须保留真实构建验证，但构建只能由用户在Qt Creator中执行。Agent不得以任何理由在命令行、脚本、后台进程或GUI自动化中尝试完整或局部编译，也不得启动Qt Creator代替用户构建。

明确禁止Agent运行或间接调用：

```text
qmake
nmake
jom
msbuild
cmake --build
devenv
Qt Creator Build/Rebuild/Run
任何会编译、链接或启动本项目及测试目标的脚本或命令
```

Agent只允许执行轻量静态检查，例如：

- 阅读和搜索源码、调用关系、Qt信号槽与UI自定义控件引用；
- 检查include、声明/定义、文件名大小写和明显的C++语法结构；
- 检查新增文件是否正确加入 `.pro/.pri`、`.ui`、`.qrc` 或其他现有工程清单；
- 检查Git差异、空白错误、无关改动和旧符号剩余引用；
- 生成测试源码、固定样本清单和用户可在Qt Creator中执行的验证步骤，但不编译或运行这些测试。

每个代码切片完成静态检查后，必须按以下流程处理：

1. 将功能状态保持为 `迁移中`，在执行记录中标注“静态检查通过，等待用户Qt Creator构建”。
2. 暂停依赖该切片的后续代码迁移，明确告诉用户本次改了什么，以及应在Qt Creator中执行什么。
3. 新增/删除源码或修改 `.pro/.pri` 时，请用户先执行 Run qmake，再执行Build或Rebuild；普通源码修改通常只需Build/Rebuild。Clean只在阶段收口或怀疑旧构建产物干扰时建议，不要求每次执行。
4. 用户反馈构建失败时，只根据用户提供的完整错误信息定位和修复，再次静态检查并交回用户复编。
5. 用户确认构建和本切片必要回归通过后，才能标记 `已验证`、创建该代码切片的正式Git提交并继续下一个依赖切片。

纯文档、盘点和不改变构建输入的记录更新不需要用户编译，可以在静态核对后独立提交。不得因为Agent不能自行构建就取消构建门禁，也不得把“静态检查通过”写成“编译通过”。

### 5. 必须保持的边界

- 保持 Qt 5.14、qmake、MSVC2017和C++11，不升级工具链、SDK、OpenCV、PaddleOCR或模型。
- 五种检测模式、模板制作与加载、多Profile选择、字符切割、单个和批量参数编辑、绘图交互、相机与PLC操作、统计、存图、设置、启动保护、日志和退出清理等现有功能都必须先盘点，再迁移或优化。
- 不要求兼容旧产品模板、旧设置或旧数据格式，但制作、保存、加载和使用产品数据的能力不能丢失。
- 阶段0至阶段3保持当前相机、PLC、硬触发、0/49写入、约100毫秒复位、延迟剔除和正常结果输出行为。
- 相机曝光、增益等当前仍是整机设置；`calibrate_config.yaml` 和纸巾 `roughnessThreshold` 属于产品配方。纸巾阈值新建默认值统一为6.0，检测器不得保留第二个业务默认值。
- 产品配方、相机参数、PLC参数、检测间隔、延迟剔除和存图策略只允许停止检测后修改，并在下次启动检测时生效。
- 当前软件不能控制传送带。只能表述为“视觉检测暂停、禁止受理或报警”，不能声称传送带已经停止。
- 多相机本轮延期：保留现有源码、接口和入口，不迁移、不删除、不扩建，不接入正式统计和PLC结果链。
- 不使用 `QThread::terminate()`，不让长期记录持有原图，不引入无界帧队列或无界存图队列。
- 不为目录整齐而批量移动文件；职责迁移、入口接入、验证和旧引用清理必须在同一可审查切片中完成。
- 遵守计划书2.5节的目录、文件、类型、函数、信号槽、变量、常量、JSON字段和测试命名规则。

### 6. 开始前的强制检查

开始修改前必须：

1. 查看当前分支、HEAD、工作区状态和已有未提交修改；把已有修改视为用户资产，不覆盖、不回退、不混入无关提交。
2. 确认当前阶段、当前切片和上一个阶段门禁是否真实通过，不依据对话记忆猜测进度。
3. 检查功能对照表和重构执行记录是否存在、是否完整。
4. 从原UI入口、定时器、线程、相机/PLC回调或脚本入口追踪本切片的完整调用链。
5. 为本切片列出受影响的全部功能ID。没有功能ID或尚未达到 `已基线` 的可达功能，不得直接迁移或删除。

如果阶段0尚未完成，只执行阶段0，先建立真实基线；不得以“文件已扫描”或“工程能编译”代替功能基线。

### 7. 连续执行方式

按计划书的阶段0、阶段1、阶段2、阶段3顺序工作。每次只选择一个能独立验证、能安全回滚的最小切片：

```text
追踪旧实现
→ 更新功能对照表
→ 提取一个职责并接回原入口
→ Agent完成轻量静态检查
→ 用户在Qt Creator中构建和回归
→ 更新状态和执行记录
→ 创建本地Git提交
→ 继续下一个切片
```

阶段内不要求用户逐切片批准设计方案；但代码切片到达Qt Creator构建门禁后必须暂停，收到用户构建和必要回归通过的反馈后再提交并继续。纯文档和盘点切片可以连续执行。持续通过简短 commentary 汇报当前阶段、切片、功能ID和验证进展。

只有出现以下真正阻塞时才暂停并详细询问用户：

- 需要删除、合并或延期一个当前可达功能；
- 需要改变OK/NG判定、阈值语义、模板选择、统计口径或操作结果；
- 需要改变PLC写值/顺序、相机或硬触发时序、延迟剔除或设备行为；
- 工作必须提前进入阶段4才能继续；
- 用户已有修改与当前切片直接冲突且无法安全保留；
- 必需的设备、样本或业务预期只能由用户提供。

能通过阅读源码、搜索引用、运行现有检查或缩小切片解决的问题，不要重新问用户。

### 8. 功能保全门禁

重构的保全单位是“可观察功能”，不是旧文件或旧类名。每个功能ID都必须记录：入口、前置条件、操作步骤、参数和默认值来源、正常与失败结果、副作用、旧调用链、目标位置、验证方式和证据。

每个切片必须满足：

- 修改前，相关功能ID至少为 `已基线`。
- 旧入口先接入新职责，固定输入下的新旧判定、文本、关键几何结果和副作用一致，或差异属于计划明确批准的优化。
- 从原入口检查UI提示、设置、文件、统计、存图、日志和硬件副作用，不能只测试新类。
- Agent静态检查结束但用户尚未确认Qt Creator构建和回归时，相关功能保持 `迁移中`；收到通过反馈后才能更新为 `已验证`。
- 旧实现只有在替代实现已验证且全仓搜索确认零引用后才能删除。
- 任何不能实际运行的验证都要记录具体原因和剩余风险，不能写成“理论上等价”。

### 9. Git提交与回退规则

Git用于把每个已经验证的阶段性结果变成独立回退点，不是等整个阶段做完后只提交一次。

1. 开始时记录基线HEAD。若当前没有专用重构分支，创建 `codex/ocrgangyin-refactor`；若该分支名已存在或当前分支已经是合适的 `codex/` 重构分支，安全沿用并在执行记录中说明。
2. 工作区已有修改不得丢弃、覆盖或擅自暂存。只暂存当前切片明确涉及的文件，不使用会混入未知改动的粗放暂存方式。
3. 每完成一个“已接回原入口、用户已确认Qt Creator构建和必要回归、可独立回滚”的最小代码切片，就创建一次本地提交；纯文档切片在静态核对后可以提交。阶段门禁完成时再创建阶段收口提交，但没有新变化时不创建空提交。
4. 提交前必须更新功能对照表和执行记录。Agent只执行本文件允许的轻量静态检查；代码切片必须同时取得用户提供的Qt Creator构建/回归结果。用户尚未确认、验证失败或功能状态仍为 `迁移中` 时，不创建伪装成完成的代码提交。
5. 每个提交只包含一个切片或一个阶段收口，不混入依赖升级、全局格式化、多相机扩建、算法调参或其他无关工作。
6. 禁止使用 `git reset --hard`、强制检出覆盖用户文件、变基改写已有历史或强制推送。未经另行授权不执行 `git push`。
7. 将提交哈希、阶段、切片、功能ID、验证命令和结果写入 `OCRGangYin重构执行记录.md`。由于提交哈希只能在提交后获得，可在下一次记录更新或阶段收口提交中补记，不为补一个哈希反复制造无意义提交。

提交信息使用清楚的中文或中英混合语义，推荐格式：

```text
docs: 建立阶段0功能基线
refactor(recipes): 迁移纸巾产品参数
refactor(detection): 提取纸巾检测流水线
refactor(devices): 接入现有相机适配器
refactor(runtime): 增加有界图片保存队列
refactor(ui): 移出已验证的检测业务职责
test(detection): 补充二维码模式回归样本
```

### 10. 各阶段停止条件

- 阶段0：所有当前可达功能都有唯一ID、完整调用链和可执行基线，五种模式及UI/模板/设备/统计/存图/设置/启动/退出路径均已覆盖。
- 阶段1：新配方格式和五种Pipeline由旧代码拆解形成，模板工作流能力保留，离线对照通过，硬件主链未改变。
- 阶段2：设备窄接口、统一运行协调、结果临时交接和容量为8的有界存图队列接入；现有正常PLC时序不变。
- 阶段3：有界帧队列、协作停止、串行检测线程和UI职责拆分完成；无持续积压、图像长期持有或残留线程。

阶段3门禁通过后停止开发，汇报阶段0至阶段3的提交链、功能状态、Agent静态检查、用户Qt Creator构建/回归证据和仍需现场验证的内容。明确说明阶段4尚未执行，并列出进入阶段4前真正需要用户确认的事项。

### 11. 每次汇报格式

先给结论，再简要列出：

1. 当前阶段和切片；
2. 涉及的功能ID；
3. 从哪些旧代码提取到哪些新位置；
4. 保持不变的行为和计划内优化；
5. Agent实际执行的静态检查，以及用户反馈的Qt Creator构建、测试与回归结果；
6. 本次本地提交哈希；
7. 下一切片或真正阻塞项。

不要只汇报计划。只要仍有安全、已授权且不依赖用户答复的工作，就继续实施。
