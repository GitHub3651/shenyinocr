# OCRGangYin 工业视觉框架升级计划（精简版）

## 一、重构目标

本次重构只解决以下问题：

- `widget.cpp` 职责过多，算法、设备、线程、设置、存图和界面互相混杂。
- 五种检测模式存在重复流程，新增功能需要继续修改主窗口。
- 相机、PLC、OCR和二维码对象缺少清晰边界。
- 线程、停止流程和图像所有权不够明确。
- 产品参数分散，后续增加产品或检测模式不方便。

目标架构为：

> 精简的模块化单体 + 产品配方 + 可复用检测流水线 + 统一运行控制。

模块和文件按职责划分。相关的小型类型集中维护，能够独立测试或需要替换实现的职责再提取为独立类。

### 实施原则：以现有代码为事实来源，先拆解再优化

本轮不是脱离现有程序重新开发一套新软件，而是以当前 `app/` 为事实来源，将已经运行的代码逐段抽取、重组到目标模块中。

- 每次迁移前必须先阅读并追踪 `app/` 中对应的真实调用链、参数来源、界面入口、线程行为、存图、统计和PLC副作用，不能只按计划书或理想接口重新实现。
- 当前界面或运行流程能够触达的功能都必须在功能对照表中标明新位置、验证方式和迁移状态；没有明确去向的功能不得删除。
- 第一遍迁移只做职责抽取、依赖收口和必要的接口适配，保持现有输入、输出、判定、提示和正常硬件时序；代码进入新模块并通过对照后，再做有界队列、安全保存等已确认优化。
- 现有类优先通过移动代码、提取函数或增加薄适配层复用，不在尚未完成对照时从零重写同一功能。
- 当前代码、界面说明和计划发生冲突时，先记录差异并以可复现的实际运行行为建立基线；任何业务行为调整都要单独确认，不能在结构重构中顺带改变。
- 一个旧实现只有在替代实现通过回归、功能对照表已完成且确认零引用后才能删除；Git负责保留历史，不在源码中长期维护两套实现。

### 已确认的边界

- 保持 Qt 5.14、qmake、MSVC2017/C++11。
- 软件尚未上线，不兼容旧产品模板、旧配置和旧目录；新版本直接使用新格式。
- 保持五种算法的现有判定、阈值、模型和正常PLC时序，不借重构调整准确率。
- 产品配方、相机参数、PLC参数、检测间隔、延迟剔除和存图策略只能在停止检测后修改，下次启动检测时生效。
- 相机曝光、增益等参数暂时属于整机设置，不随产品配方变化。
- `calibrate_config.yaml` 属于产品配方资源。
- 纸巾检测允许没有模板；`roughnessThreshold` 属于纸巾产品配方，新建默认值为6.0，检测器不再保留另一套业务默认值。
- 单相机是本轮正式生产链；现有多相机功能保留，但不接入正式统计和PLC结果链。
- 当前有效的模板制作、模板加载、多Profile选择、字符切割、单个和批量参数编辑、相机与PLC操作、统计清零、设置恢复、启动保护和日志功能必须保留，允许在不改变使用结果的前提下优化内部实现。
- 前期算法和软件结构重构不改变现有相机、Snap7、0/49写入、约100 ms复位和延迟剔除行为。
- 当前软件不能控制传送带停止。任何软件 `Fault` 都只表示视觉检测暂停，不能显示“传送带已停止”。
- 构建验证必须保留，但只由用户在Qt Creator中执行；Agent只做轻量静态检查，不运行或间接调用 `qmake`、`nmake`、`jom`、`msbuild`、`cmake --build`、`devenv`，也不通过GUI自动化触发Qt Creator构建。

### 开发执行中的构建分工

- Agent负责阅读和修改代码、检查调用和信号槽、检查include与声明/定义、确认新增文件已加入 `.pro/.pri/.ui/.qrc`、搜索旧引用并执行Git差异检查。
- Agent可以编写测试源码和验证步骤，但不得自行编译、链接、运行主程序或测试目标，也不得启动Qt Creator代替用户构建。
- 每个代码切片完成静态检查后，功能状态保持 `迁移中`，执行记录标明“静态检查通过，等待用户Qt Creator构建”；暂停依赖该切片的后续代码迁移。
- 新增/删除源码或修改 `.pro/.pri` 时，由用户在Qt Creator中先Run qmake再Build/Rebuild；普通源码修改通常只需Build/Rebuild。Clean只在阶段收口或怀疑旧构建产物干扰时执行。
- 用户反馈构建失败时，Agent根据完整错误信息修复并再次交回用户验证；用户确认构建和必要回归通过后，功能才能标记为 `已验证`，代码切片才能创建正式Git提交并继续。
- 纯文档和盘点切片不要求构建，可以在静态核对后提交。最终Release性能、连续运行和现场硬件验证仍由用户或现场人员执行并提供结果。

## 二、精简目标架构

### 2.1 目录

```text
app/
├─ startup/          # main和对象组装
├─ ui/               # 界面和显示
├─ recipes/          # 产品配方
├─ detection/        # 检测类型、Tool、Pipeline和五种模式
├─ devices/          # 相机、PLC、OCR和二维码接口及实现
├─ runtime/          # 启停控制、线程、队列和结果处理
└─ system_support/   # 软件设置、日志和图片保存
```

相关的小型枚举和结构体集中放在所属模块的类型头文件中；承担清晰职责的类使用独立文件。

### 2.2 依赖方向

```text
startup → 所有模块
ui → runtime + recipes
runtime → recipes + detection + devices + system_support
detection → recipes + devices中的OCR/二维码接口
recipes → Qt Core/OpenCV基础类型
devices → 第三方SDK
system_support → Qt Core/OpenCV基础类型
```

约束：

- `detection/` 不访问UI、PLC、相机SDK和磁盘保存。
- `ui/` 不持有相机SDK对象、PLC客户端、OCR模型或DLL函数指针。
- `recipes/` 不执行定位、OCR、二维码或正式检测。
- `runtime/` 负责编排，不实现具体算法。
- 具体第三方依赖只出现在 `devices/`、`system_support/` 和现有 `third_party/` 中。

### 2.3 主运行链

```text
UI命令
  → RuntimeController
  → CaptureWorker
  → 有界FrameQueue
  → DetectionWorker
  → DetectionPipeline
  → DetectionResult
  → DetectionCompletion
  → ResultHandler
      ├─ 更新计数
      ├─ 请求PLC结果
      └─ 提交图片保存
  → 生成只读结果呈现快照
  → 容量为1的ResultPresentationMailbox
  → UI Presenter一次呈现完整产品结果
```

`ResultHandler` 是一次检测结果的唯一入口。同一 `ProductKey` 只能提交一次结果、更新一次统计并请求一次PLC逻辑结果。

`DetectionCompletion` 只负责把本次检测使用的只读帧和 `DetectionResult` 一起交给 `ResultHandler`。它不是长期记录，处理结束后只有有界存图任务可以继续短期持有图像。

结果显示同样以 `ProductKey` 为边界。结果图、Overlay、识别文字、命中Profile/模板名、OK/NG、统计和耗时必须组成一个只读呈现快照，并在UI线程一次整体应用；不得通过彼此独立的排队信号分别更新。呈现邮箱容量固定为1，UI尚未消费上一件完整结果时，检测完成侧等待空位，以反压方式限制正式结果积压。

Stage 3迁移期间允许旧 `Widget` 通过容量为1的完成邮箱一次执行原有整套结果槽，作为兼容桥保留已验证副作用；这只是过渡实现。最终由 `ResultHandler` 组织运行副作用、由UI Presenter消费只读呈现快照，`Widget` 不继续拥有检测线程、结果处理或呈现邮箱的业务实现。

### 2.4 现有功能保全机制

重构保全的单位不是“文件还在”或“类名还在”，而是操作人员和程序外部能够观察到的一项完整行为。一个类可能承载多项功能，一项功能也可能跨越UI、设置、线程、算法、存图和PLC多个文件；必须按真实调用链建立对应关系，不能根据目标架构猜测功能已经被覆盖。

阶段0必须先建立 `docs/development/OCRGangYin现有功能对照表.md`。每项功能使用唯一ID，并至少记录：

| 字段 | 内容 |
|---|---|
| 功能入口 | 按钮、菜单、鼠标/键盘操作、启动流程、定时器、相机/PLC回调或其他触发条件 |
| 前置条件和操作步骤 | 在什么模式和状态下可用，用户或设备怎样触发 |
| 当前可观察结果 | 画面、提示、按钮状态、检测结果、设置恢复、生成文件和错误反馈 |
| 输入与参数 | 参数来源、默认值、产品/整机归属和生效时机 |
| 副作用 | 统计、存图、日志、PLC写入、线程和对象生命周期变化 |
| 旧实现 | 入口函数、完整调用链和关键源码位置 |
| 新位置 | 目标模块、类或函数，以及保留或计划内优化的说明 |
| 验证 | 自动测试、固定样本或可重复的人工操作步骤和实际证据 |
| 状态 | `待盘点 / 已基线 / 迁移中 / 已验证 / 已延期 / 已确认删除`；后两项必须分别有计划依据或用户确认记录 |

盘点必须同时从以下入口反向核对，不能只扫描五种算法：

- 所有可见页面、按钮、菜单、输入控件、状态显示、对话框，以及鼠标、键盘和绘图交互。
- `.ui` 自定义控件、显式和自动信号槽连接、定时器、线程回调、相机回调、PLC回调和旧式字符串连接。
- 模板制作、加载、切割、编辑、多Profile、模式记忆和配方资源操作。
- 相机、PLC、软硬触发、开始、停止、参数下发和状态恢复。
- 设置默认值、保存、加载、清除、恢复、运行中禁用和下次启动生效。
- 原图/标注图显示、统计、清零、存图组合、路径、日志、错误提示和失败回退。
- 启动保护、授权、单实例、崩溃处理、部署检查、正常退出和资源释放。
- 当前仍可进入的独立工程或延期功能；延期也必须登记，不能因本轮不迁移而从清单消失。

强制规则：

1. 每个迁移切片开始前先列出受影响的功能ID；没有功能ID的代码不得直接迁移或删除。
2. 新代码编译通过只代表结构可构建，不代表功能已保留。必须从原入口完成操作，并核对结果、提示、设置、文件、统计和硬件副作用后才能标记 `已验证`。
3. 迁移期间可以由旧入口调用新实现；在相应功能全部 `已验证` 前，旧路径和必要适配不得删除。
4. 怀疑是无用代码时，必须检查普通调用、Qt信号槽、`.ui` 自定义控件、定时器、回调、脚本和动态入口。只有确认零引用、没有对应可观察功能并记录证据后才是可删除候选；仍无法确认时询问用户。
5. 类和函数允许拆分、合并或改名，不要求逐函数机械复制；但它们承载的所有可达行为必须在功能对照表中找到新位置和回归证据。
6. 每个阶段结束时，该阶段涉及的功能不得停留在 `待盘点` 或 `迁移中`。最终完成时，全表只能是 `已验证`、有计划依据的 `已延期` 或经过用户确认的 `已确认删除`。
7. 任何新旧差异都必须分类为“内部实现变化”或“用户确认的行为变化”。没有确认的输入、输出、提示、正常时序和操作结果默认保持现状。

例如 `ImageLabel` 不是只登记成“一个绘图类还在”，而要拆成图像自适应显示、定位框、二维码框、多边形、重置、坐标换算、状态清理和事件转发等独立行为；它们验证完成后，该类才可以按UI职责移动到 `ui/widgets/image_label.h/.cpp`。其他现有类和功能全部执行同一规则，不对 `ImageLabel` 特殊处理。

### 2.5 文件、类型和函数命名规则

命名以“看到名称就能判断职责”为目标。新代码必须遵守；旧代码只在对应职责迁移时改名，不单独进行全项目批量重命名，也不修改第三方SDK提供的名称。

| 对象 | 规则 | 示例 |
|---|---|---|
| 目录 | 全小写；多个单词使用下划线；使用计划规定的职责名，不增加含义模糊的杂项目录 | `system_support/`、`ui/widgets/` |
| C++文件 | 全小写下划线；通常一个主要类对应一组同名 `.h/.cpp`；名称由主要类型转换而来 | `runtime_controller.h/.cpp`、`image_label.h/.cpp` |
| UI和资源文件 | 全小写下划线，名称说明页面或用途 | `recipe_editor_page.ui`、`app_resources.qrc` |
| 类型 | 类、结构体和枚举类型使用PascalCase；名称使用业务含义，不使用无意义的 `Data1`、`Info2` | `ProductRecipe`、`DetectionResult`、`RuntimeState` |
| 接口与实现 | 可替换设备接口使用 `I` + PascalCase；实现类使用厂商或技术名称 + 职责后缀 | `ICameraDevice`、`HikvisionCameraDevice` |
| 函数 | lowerCamelCase；命令以动词开头，查询函数使用名词或 `is/has/can`，避免含糊的 `doWork()`、`process2()` | `startDetection()`、`loadRecipe()`、`trackingRect()`、`isRunning()` |
| Qt信号 | lowerCamelCase，描述已经发生的事件或状态，不增加 `signal_` 前缀 | `detectionCompleted()`、`templateGuideChanged()` |
| Qt槽函数 | 使用业务动作命名并显式 `connect`；新代码不使用控件编号形成业务名称 | `handleStartDetection()`，不新增 `on_pushButton_6_clicked()` |
| 变量和参数 | lowerCamelCase；私有成员增加 `m_`；布尔值使用 `is/has/can/should` 说明真假含义 | `recipeId`、`frameCount`、`m_isRunning` |
| 常量 | 代码内常量使用 `k` + PascalCase；宏才使用全大写下划线，并尽量只用于编译开关 | `kImageSaveQueueCapacity`、`OCR_ENABLE_TRACE` |
| 枚举值 | 使用PascalCase，不携带重复的枚举名前缀 | `DetectionStatus::SystemFault` |
| JSON字段 | 使用lowerCamelCase，并与对应数据成员含义一致 | `schemaVersion`、`roughnessThreshold` |
| 测试文件 | 被测对象文件名 + `_test.cpp`，测试用例名称说明条件和预期 | `recipe_store_test.cpp` |

补充规则：

- 常见缩写在类型名中按单词处理：`Ocr`、`Plc`、`Roi`，保持 `IOcrEngine`、`IPlcDevice` 这类既有接口形式；文件名分别写成 `ocr_engine.h`、`plc_device.h`。
- 角色后缀统一：持久化用 `Store`，流程编排用 `Controller`，线程执行对象用 `Worker`，设备边界用 `Device`，第三方算法封装用 `Engine` 或 `Adapter`，检测组合用 `Pipeline`，单步骤用 `Tool`。
- 不创建含义不明的 `common.*`、`utils.*`、`helper.*` 作为代码堆放处。小函数留在所属模块；确有多个调用方且职责明确时，按具体能力命名。
- `.ui` 控件对象名使用“业务含义 + 控件类型”的lowerCamelCase，例如 `startDetectionButton`、`detectionModeComboBox`；Qt自动生成文件不手工修改。
- 新增公开函数前先确认调用方。只被类内部使用的函数保持 `private`，不要为了方便把实现细节暴露成公共接口。
- 文件改名必须与职责迁移在同一切片完成，同时更新 `.pro/.pri`、`.ui` 自定义控件头文件、include和大小写一致性；用户在Qt Creator确认构建和回归通过后才删除旧文件名。

## 三、核心设计

### 3.1 产品配方

正式数据结构：

```text
<ApplicationData>/
├─ settings/
│  └─ app_settings.json
├─ recipes/
│  └─ <recipe_uuid>/
│     ├─ recipe.json
│     └─ assets/
│        ├─ tracking_template.bmp
│        ├─ calibrate_config.yaml
│        └─ character_templates/
└─ diagnostics/
```

`recipe.json` 示例：

```json
{
  "schemaVersion": 1,
  "recipeId": "f3c8c52d-7c51-4a0f-8df4-95d0d8fe3dc2",
  "displayName": "纸巾产品",
  "detectionMode": "tissue",
  "parameters": {
    "roughnessThreshold": 6.0
  },
  "assets": {}
}
```

规则：

- `recipeId` 是系统生成、不可修改的UUID；`displayName` 是可修改的中文显示名称。
- 每种模式使用自己的类型化参数结构。
- 纸巾配方可以没有任何资源文件。
- 字库匹配和二维码+三期必须保留当前一次加载多个产品模板并自动选择Profile的能力；对应配方允许包含一个或多个Profile，每个Profile独立保存名称、定位模板、ROI、目标字符、图像阈值、字符模板和适用的二维码参数。
- 新配方界面必须继续支持当前的实时取景、冻结框选、模式化ROI引导、二维码区域验证、字符模板切割与命名、单个Profile编辑和批量编辑；配方存储格式可以改变，现有使用能力不能因改用 `RecipeStore` 而消失。
- 配方资源必须复制到当前产品的 `assets/`，运行时不引用外部绝对路径。
- `RecipeStore` 负责加载、校验和安全保存。保存时先在正式产品目录的同级临时目录写入 `recipe.json` 和全部资源，再重新加载并校验Schema、模式参数、必需资源、图片、YAML和资源路径。
- 临时目录全部校验成功后，才执行可回滚的整套目录替换：已有正式目录先改名为临时备份，再提交临时目录；提交失败时恢复原目录，成功后删除备份。
- 任一步骤失败都删除未提交的临时数据并继续使用最后一次有效配方，不允许正式产品目录处于只更新了部分文件的状态。
- 启动检测时创建一份只读 `ProductRecipe` 副本，本次运行只读取该副本。

### 3.2 软件设置

`app_settings.json` 保存整机和运行设置，包括：

- 相机标识、曝光、增益和触发参数。
- PLC连接参数和当前地址映射。
- 检测间隔和延迟剔除参数。
- 图片保存目录、保存范围和原图/标注图选择。

设置通过一个 `AppSettingsStore` 读写。界面运行中禁用编辑，`RuntimeController` 再次拒绝运行中应用，避免只依赖UI状态。

### 3.3 检测类型和Pipeline

只保留必要类型：

- `ProductKey`：本次运行ID加递增序号。
- `FrameData`：产品标识、帧号、相机号、时间和原图。
- `DetectionRequest`：只读帧和只读产品配方。
- `DetectionResult`：算法判定、检测状态、识别文本、Overlay和耗时，不保存原图。
- `DetectionCompletion`：检测完成后的临时传递对象，包含只读 `FrameData` 和 `DetectionResult`。
- `AlgorithmVerdict`：`NotEvaluated / Ok / Ng`。
- `DetectionStatus`：`Completed / SystemFault / Cancelled`。

```cpp
struct DetectionCompletion
{
    std::shared_ptr<const FrameData> frame;
    DetectionResult result;
};
```

该结构放入现有检测类型头文件，不为它单独建立模块或长期存储；它只在检测完成、结果处理和存图任务提交期间存在。

`AlgorithmVerdict` 只表示产品质量；相机、模型、DLL、线程等问题使用 `SystemFault`，不能混成产品NG。

Tool接口保持简单：

```cpp
class IDetectionTool
{
public:
    virtual ~IDetectionTool() {}
    virtual ToolResult execute(DetectionContext &context) = 0;
};
```

`ToolResult` 只需要：继续、OK结束、NG结束、系统故障、取消。

五种Pipeline：

```text
模板匹配：定位 → 日期ROI → 字符匹配 → 钢印重叠 → 判定
字库匹配：Profile选择 → 定位 → 日期ROI → 字符匹配 → 数量判定
深度模型：定位 → 日期ROI → PaddleOCR → 文字清洗 → 目标比较
纸巾检测：纸卷检测 → 粗糙度规则 → 判定
二维码+三期：Profile选择 → 定位 → ROI → 二维码 → 字符匹配 → 判定
```

新增模式只增加或复用Tool、装配Pipeline、注册模式并增加UI名称，不修改主窗口中的算法分支。

### 3.4 设备封装

只为确实需要替换或模拟的设备建立接口：

- `ICameraDevice` / `HikvisionCameraDevice`
- `IPlcDevice` / `Snap7PlcDevice`
- `IOcrEngine` / `PaddleOcrEngine`
- `IBarcodeDecoder` / `BarcodeDecoderAdapter`

接口返回结构化成功或失败信息，不弹对话框。UI提示由上层根据错误代码生成。

PLC正常行为保持当前实现：

- OK执行一次写0。
- NG执行写49、等待约100 ms、再写0复位。
- NG后的写0只是同一次NG命令的复位，不是第二件产品结果。
- 没有PLC确认位时，只能记录“写入调用成功”，不能记录“机械剔除已确认”。

### 3.5 Runtime、线程和结果处理

`RuntimeController` 负责：

- 选择配方、检查设置和设备是否就绪。
- 启动与停止检测。
- 创建本次运行ID和只读配置。
- 管理 `CaptureWorker`、`DetectionWorker` 和 `ResultHandler`。
- 拒绝运行中修改生产参数。

Runtime状态只保留：

```text
Idle → Starting → Running → Stopping → Idle
任一运行状态 → Fault → Idle（人工确认并恢复后）
```

线程规则：

- 相机采集和检测不在UI线程执行。
- 单相机检测先保持串行，不并发调用同一模型。
- 非生产实时预览只保留最新帧，允许较旧预览被更新画面覆盖。
- 正式软触发采用需求驱动串行节拍：每轮先记录相机帧序号，执行一次软触发，等待并取得序号已增加的新帧，再提交正式检测；已经受理为产品帧的输入不得被下一帧覆盖或因队列满而丢弃。
- 软触发正式链的检测队列、结果呈现邮箱和存图队列均使用有界等待反压。检测、UI呈现或存图变慢时，采集随之减速；处理足够快时，上限由相机真实触发帧率决定。
- `cameraDelay = 0` 表示不增加软件等待，大于0表示两次正式受理之间的最小毫秒间隔；不得再叠加另一段固定休眠。
- 硬触发继续使用有界FIFO；其溢出与故障归类保持到阶段4处理，本次软触发节拍优化不改变硬触发受理规则。
- 使用协作式停止和实际退出信号，不调用 `QThread::terminate()`。
- 停止时先禁止新受理，再取消检测队列、结果呈现邮箱和其他可能阻塞生产者的等待，最后协作等待线程实际退出。
- 线程未退出前不删除线程或工作对象。
- 停止后拒绝旧运行ID的迟到结果。

图像规则：

- 队列入队前取得独立图像所有权。
- 检测、最新UI显示和异步存图可以短期共享只读帧。
- UI只显示最新一个完整产品结果，不提供历史原图浏览；这里的“最新”是下一件完整呈现快照整体替换上一件，不是图片、文字、统计各自选择最新事件。
- 正式检测期间，非产品实时帧和定位Pose在进入Qt事件队列前抑制，不能覆盖当前产品结果图，也不能移动上一件产品的Overlay。
- 正式结果不得依赖无界Qt排队信号积压；容量为1的结果呈现邮箱在整套UI更新完成前持续占用槽位。
- `DetectionResult`、计数和长期记录不持有原图。
- 存图完成或实际写入失败后释放图像引用。
- 异步存图使用容量为32个产品任务的有界队列和2个后台写入线程；一个产品只提交一个任务，由该任务按设置保存原图、标注图或两者。
- 存图队列满时不丢弃新任务；提交侧继续持有当前检测图并等待空位，以降低检测吞吐的方式施加反压。队列只吸收正常写盘过程中的短时峰值，不作为无限积压缓存。
- 正常磁盘条件下已完成检测且命中保存策略的每件产品都必须提交存图；只有目录、权限、磁盘空间或设备等实际写入失败才允许缺图，并向UI发送累计红色报警。实际写入失败不改变已经产生的算法结论。

`ResultHandler` 直接组织统计、PLC调用和图片保存。某项职责增长到能够独立测试或需要替换实现时，再提取为独立组件。

正常产品统计保留当前口径并集中实现：

```text
产品质量合格率 = OK /（OK + 产品NG）
```

`ResultHandler` 统一维护OK和产品NG数量。系统故障、取消和未确认结果分别计数，不计入产品NG和产品质量合格率分母。阶段1至阶段3不提前改变现有PLC异常处理行为，PLC断线、队列溢出和系统故障对应产品的最终处理仍在阶段4实施。

### 3.6 多相机

多相机不是本轮重点。现有多相机源码、`IMultiCameraProvider` 和界面入口保持原状，本轮不做目录迁移、不建立公共 `.pri`、不接入单相机正式统计、PLC结果或生产Runtime。只要求单相机重构期间主程序仍能正常编译，现有多相机入口不因本轮修改而被破坏；后续需要时再建立独立升级任务。

### 阶段4：生产异常策略和最终清理

本阶段才改变PLC断线、硬触发FIFO溢出、结果重复和系统故障行为。

- PLC断线、硬触发队列溢出或无法保证单件唯一结果时，视觉系统进入 `Fault`，停止新的正式检测和结果输出。
- 软件持续报警，明确提示传送带状态未知，需要操作员使用传送带自身控制人工停线并隔离产品。
- 进入 `Fault` 后，即使相机仍继续产生图像，新到达帧也不得创建正式 `ProductKey` 或进入 `FrameQueue`，收到后立即释放并累计故障后丢弃帧数量。
- `FrameQueue` 中尚未开始检测的帧停止进入正式检测；这些帧和正在检测的产品均按后文的一次NG请求或未确认规则完成收尾，再释放图像引用。
- 对进入 `Fault` 后才到达的新帧，不得更新正式产品统计或请求PLC结果；Fault前已经接收的产品只能按后文规则完成一次收尾。视觉软件只能说明正式检测链已暂停，不能声称相机、传送带或机械机构已经停止。
- 已经提交的算法结论不得被系统故障覆盖，也不得重复写PLC。
- 尚无最终结论、产品身份明确且PLC仍可写时，可以沿用当前49/约100 ms/0流程请求一次NG；否则记录为未确认，不伪造剔除成功。
- 普通图片保存失败仍只报警并继续检测。
- 现场确认PLC是否提供触发计数、产品编号或结果确认位；未确认的能力一律按不存在处理。
- 各阶段已经验证的源码随对应职责移动到目标模块；本阶段只清理功能对照表中已完成替代且确认零引用的剩余旧实现，并更新主工程源码清单。

- `detection_tests`：五种Pipeline的OK/NG、识别文本、ROI、扫码短路和取消。
- `runtime_tests`：参数门禁、唯一结果、产品合格率、异常结果独立计数、PLC调用次数、存图队列满时等待且不丢任务、帧队列、容量为1的结果呈现邮箱、生产者反压、取消唤醒、停止、迟到结果、Fault后拒收新帧和图像释放；使用Fake设备。

除自动测试外，每阶段都按阶段0功能对照表逐项执行人工冒烟检查。至少覆盖模板制作与加载、多Profile自动选择、字符切割和批量编辑、图像显示与ROI绘图交互、相机开关、PLC连接与参数操作、统计清零、存图组合、设置清理与恢复、授权启动、单实例、日志和正常退出。每项必须记录实际结果，不能用一条笼统的“界面正常”代替多个功能ID的验证。

统一回归要求：

- 新旧算法对同一固定样本的最终判定一致。
- 识别文本和关键几何结果一致；允许的像素与浮点误差在样本清单中明确。
- 每种模式原则上至少5个代表性OK和5个NG样本；不足时记录原因。
- 二维码模式必须覆盖不可读、可读且日期OK、可读且日期NG。
- 连续软触发必须分别验证`cameraDelay = 0`和非0最小间隔；核对采集随检测/UI/存图能力反压，且停止后能够再次启动。
- UI回归必须核对同一产品的图像、Overlay、识别文字、模板名、OK/NG、统计和耗时同步替换，不接受仅日志继续而画面停留，或图片与文字来自不同产品。
- 由用户在Qt Creator的Release构建下记录算法P50/P95和最大队列深度，重构后不得出现明显退化。
- 最终现场以200件/分钟连续运行至少30分钟，再按正常节拍运行至少4小时，检查结果对账、队列和内存趋势。
- 每个经过用户构建/回归确认的代码切片独立提交；每个阶段另做收口提交，不混入依赖升级、全局格式化或算法优化。纯文档切片可以在静态核对后提交。

## 六、本轮范围

本轮完成单相机正式生产链的模块化重构。以下工作如有需要，分别建立后续任务：

- 多相机正式生产接入。
- 多相机源码目录整理、公共 `.pri` 和独立工程共用构建清单。
- UI视觉样式重新设计。
- Qt6、CMake、C++17、OpenCV、PaddleOCR或模型升级。
- 算法阈值、准确率和PLC地址调整。
- 旧产品数据的人工整理或迁移。

## 七、完成后的维护规则

- 新增产品：新增或修改产品配方，不修改主窗口算法代码。
- 新增Tool：放入 `detection/` 并增加离线测试。
- 新增检测模式：装配Pipeline、注册模式并增加UI名称。
- 更换设备：替换 `devices/` 中对应实现，不修改检测算法。
- 新增设置：先判断属于产品配方还是整机设置，每项设置只保留一个默认值来源。
- 类或文件按独立职责拆分，主窗口只保留界面组合与命令连接。
- 新文件、类型、函数、信号槽、变量、JSON字段和测试名称遵守2.5节；迁移旧职责时同步消除同一模块内明显不一致的名称，但不做脱离功能迁移的全局改名。
- 功能对照表是删除旧代码和宣告重构完成的强制依据；新增、修改或删除用户可达功能时同步更新对应功能ID和回归步骤。
- 旧代码在替代实现通过回归且确认零引用后删除，历史由Git保存。
