# OCRGangYin 软硬触发启动行为两项调整方案

## 1. 状态与范围

- 文档状态：代码已实施，待用户构建与现场验收。
- 编制日期：2026-09-10。
- 编制基线：分支 `codex/ocrgangyin-refactor`，提交 `c8b1f7b`。
- 当前进度：两项生产修改已完成，源码差异与调用关系静态检查通过；未执行 Qt Creator 构建和真实设备验证。
- 当前门禁：用户在 Qt Creator 完成 Run qmake、Clean、Rebuild 和本方案验收后，才能标记为完成。

本方案只允许修改以下两项：

1. 启动时是否改变后台累计统计数据。
2. 启动成功后如何清理上一产品的界面残留。

除这两项及其必要配套代码外，不修改任何其他行为。

## 2. 统计数据与界面显示的边界

“累计统计数据”和“界面显示”属于两个层级，必须分别描述：

- 累计统计数据由 ResultService 保存，包括总数、NG 数和合格率计算基础。调用 `resetStatistics()` 会真正改变这些数据。
- 界面显示由 InspectionPage 维护，包括主图像、最终判定、识别文字、耗时、当前模板名称以及统计控件当前显示的文字。清空控件不等于修改后台统计数据。

本方案的统一目标是：启动成功后保留后台累计统计，并继续在界面显示这些统计；只清除上一产品的图像和结果信息。

## 3. 两项调整

### 3.1 启动时保留累计统计

#### 当前代码

- 软触发启动不自动调用 `resetStatistics()`，累计总数、NG 数和合格率保持不变。
- 硬触发在 `InspectionApplicationService::start()` 中、正式启动事务完成前调用 `resetStatistics()`。
- 因为清零发生在相机准备、PLC 写入和 DetectionWorker 启动之前，后续任一步失败时，原有累计统计也已经丢失。

#### 目标行为

- 删除硬触发启动专用的 `resetStatistics()` 调用。
- 软触发和硬触发启动均不得自动修改累计总数、NG 数和合格率。
- 启动失败不得改变原有累计统计。
- 本方案只取消正式识别启动时的自动清零；程序初始化、关闭相机和用户手动清零路径保持当前行为。
- 每次 Run 自身的 RunId、ProductKey sequence、接收数量和完成数量仍按现有生命周期重新建立，不属于这里保留的累计统计。

### 3.2 启动成功后只清理上一产品界面

#### 当前代码

- 软触发启动成功后没有统一清除上一产品的正式检测画面。
- 硬触发启动成功后调用 `clearInspectionView(AllDetectionData)`。
- `AllDetectionData` 同时清除上一产品图像、判定、识别文字、耗时、当前模板名称以及总数、NG 数和合格率控件，因此与“保留累计统计并继续显示”的目标不符。

#### 目标行为

- 只有 `result.isAccepted()` 确认启动成功后才执行界面清理；启动失败不得清除原检测图像、产品结果和累计统计，现有启动失败提示与操作状态刷新保持不变。
- 软触发和硬触发使用完全相同的清理路径。
- 清除上一产品的主图像、最终判定、识别文字、检测耗时和当前模板名称。
- 不清除总数、NG 数和合格率控件，并使用 Runtime 当前累计统计保证显示值与后台数据一致。
- 不再在启动成功路径调用 `AllDetectionData`。
- 优先复用现有窄操作：清除主画布并调用 `clearInspectionView(ImageMetadata)`，随后显示 Runtime 当前统计；不为该动作新增通用界面框架。
- 上述清理必须紧跟在启动成功判断之后，并位于 `result.details` 对应的“部分模板已跳过”消息框之前。该消息框会进入 Qt 嵌套事件循环；如果先显示消息框，新产品结果可能已经通过排队事件呈现，消息框关闭后再清理会误清本次 Run 的首个结果。

## 4. 实施范围

### A. 累计统计

- 在 `InspectionApplicationService::start()` 删除硬触发专用统计清零分支。
- 不修改 ResultService 的统计结构、计算方法和手动清零入口。

### B. 启动界面

- 在主窗口启动成功处理处删除硬触发专用 `AllDetectionData` 分支。
- 在 `result.isAccepted()` 失败返回之后、任何启动成功提示消息框之前，两种触发模式统一清除主画布和 `ImageMetadata`，并显示 Runtime 当前累计统计。
- 不修改其他相机关闭、Fault 恢复、模板预览或用户手动清空路径。

### C. 旧代码清理约束

- 被上述两项统一行为取代的硬触发专用统计清零分支和硬触发专用 `AllDetectionData` 分支必须直接删除，不得通过注释、条件分支或备用路径保留。
- 不新增或保留为旧行为服务的兼容接口、别名、适配器、桥接函数、转发函数、回退分支或其他胶水层。
- 仍被程序初始化、关闭相机、用户手动清零、Fault 恢复或模板预览等正式路径调用的现有接口不属于冗余代码，保持现有实现。

预计生产文件边界：

- `app/application/inspection_application_service.cpp`
- `app/ui/main_window/main_window_inspection.cpp`

## 5. 明确保持当前行为

- 检测队列策略保持不一致：软触发继续阻塞式提交；硬触发继续非阻塞提交，队列满进入现有 `HardTriggerQueueOverflow` Fault。
- 不修改 FrameQueue 容量、提交接口、条件变量、DetectionWorker 和结果顺序。
- 不修改软件触发当前取帧、回调、阻塞提交完成后再额外等待 180 ms 的节拍，不修改 Line0 外部节拍和等待语义。
- 不修改 PLC 启动准入、连接参与、运行参数写入、OK/NG 数值、延时剔除、100 ms 复位和健康检查。
- 不修改五种 Detection Pipeline、ProductKey、普通 Ok/Ng、Fault、未确认产品、统计计算、图片保存、本机 CSV 和结果呈现事务。
- 不修改设置 Schema、模板格式、UI 布局、模板预览、模板重新取景和非正式采集链。
- 不新增过载结果、排序缓存、检测队列状态机、PLC Ready/Busy、兼容层或其他功能。

## 6. 静态门禁

实施后必须确认：

1. 启动路径不存在硬触发专用 `resetStatistics()`。
2. 启动失败前后 ResultService 累计统计不变。
3. 启动成功处理不存在触发模式专用的 `AllDetectionData` 分支；软硬触发调用同一套画布和结果信息清理。
4. 启动成功后总数、NG 数和合格率继续显示 Runtime 当前累计值。
5. 启动成功清理代码位于“部分模板已跳过”消息框之前，不存在消息框关闭后再次清除检测画面的路径。
6. FrameQueue、DetectionWorker、ResultService、PLC、五种 Pipeline、存图、CSV 和设置 Schema 没有计划外差异。
7. 头文件声明、实现和 Qt 调用一致，`git diff --check` 通过。
8. 被替代的两个硬触发专用旧分支已从生产代码中删除，不存在注释保留、兼容转发、适配器、桥接函数、回退分支或其他胶水层。

## 7. 用户构建与验收

用户在 Qt Creator 执行 Run qmake、Clean、Rebuild 后验证：

1. 先产生一组累计统计，再分别启动软触发和硬触发；两种模式均保留相同的总数、NG 数和合格率。
2. 分别制造相机准备失败、PLC 准备失败和 DetectionWorker 启动失败；原累计统计和原界面内容均保持不变。
3. 软触发和硬触发启动成功后，上一产品图像、判定、文字、耗时和模板名称均被清除，累计统计继续显示原值。
4. 使用会产生“部分模板已跳过”提示的启动场景验证：提示框显示期间到达的首个新产品结果在关闭提示框后仍保留，不会被启动清理覆盖。
5. 手动统计清零入口仍能按当前规则清零，启动行为不替代用户手动操作。
6. 回归确认软触发队列满仍阻塞等待，硬触发队列满仍进入 `HardTriggerQueueOverflow` Fault；PLC、五种检测模式、统计、存图、CSV 和停止行为无其他变化。
