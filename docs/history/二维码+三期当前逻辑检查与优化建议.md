# 二维码+三期当前逻辑检查与优化建议

## 一、检查结论

当前“二维码+三期”的主流程是正确的：

```text
多模板追踪选择最佳Profile
→ 一次局部旋转，同时裁出二维码ROI和日期ROI
→ 二维码解码
→ 解码失败立即NG，日期不执行
→ 解码成功才执行字库检测
→ detectNum == targetNum 判定日期
→ 输出最终结果
```

目前不需要再增加L形定位或复杂几何搜索。后续更值得优化的是模板预检、读码策略、结果职责、并发兼容性和界面反馈。

## 二、当前做得比较好的地方

- 扫码失败后会立即短路，不进入日期检测。
- 仅启用Data Matrix，避免搜索无关码制。
- 二维码和日期只进行一次局部旋转，没有重新旋转整张相机图。
- 多Profile共享灰度图和缩小图。
- 追踪模板和字符模板已经使用缓存。
- 每个Profile能够记录上一次成功的读码策略。
- 工人框选二维码区域后会立即验证能否扫描，失败时不能继续保存模板。
- 生产界面只显示总耗时，符合当前界面要求。

主要生产流程位于：

```text
widget.cpp:2238
```

## 三、算法和架构上可以优化的地方

### 1. 当前计数逻辑正确，但单次结果通过计数变化传递

当前统计关系没有问题：

```text
总检测数 = totalImages
NG数量 = ngImages
OK数量 = totalImages - ngImages
```

二维码+三期的计数规则也是正确的：

```text
二维码失败
→ totalImages + 1
→ ngImages + 1

二维码成功、日期失败
→ totalImages + 1
→ ngImages + 1

二维码成功、日期成功
→ totalImages + 1
→ ngImages不变
```

当前单相机、同步检测条件下，这套逻辑不会造成OK/NG计数错误，无需为此立即修改。

需要注意的是，二维码扫描成功并调用日期检测后，外层代码通过调用前后`totalImages`和`ngImages`的变化，判断本次日期显示为“正确”还是“错误”。这是代码职责上的耦合，不是当前统计错误。

对应位置：

```text
widget.cpp:2367
```

如果以后接入多相机并发或后台Worker，不应该再用共享计数变化代表某一件产品的检测结果。届时建议让日期计算明确返回：

```cpp
struct WordDetectionResult
{
    bool executed = false;
    bool isOk = false;
    int targetNum = 0;
    int detectNum = 0;
    QString reason;
};
```

然后由二维码+三期综合流程统一完成一次计数、一次存图和一次PLC输出。

### 2. 检测启动前没有验证全部二维码模板

新制作模板时会扫描二维码，但加载已有模板时，不会重新完整验证：

- `BarcodeDecoder.dll`是否存在并可用；
- `tracking_template.bmp`当前是否仍能解码；
- 每个Profile的二维码参数是否有效；
- 日期多边形和字符模板是否完整。

因此旧模板损坏、模板图片被替换或DLL缺失时，软件仍可能允许启动检测，随后产品连续判为NG。

建议点击“开始检测”时，对所有已选Profile执行一次预检：

```text
DLL可用
→ tracking_template.bmp可读
→ 字符模板完整
→ 日期多边形有效
→ 全部通过才允许启动
```

如果预检失败，应一次列出所有失败的模板名称及原因。

可接入位置：

```text
widget.cpp:8369
```

### 3. 模板制作和生产时的二维码ROI处理不完全一致

框选模板时，程序扫描的是工人框选的原始矩形；生产检测时还会执行：

- 增加ROI padding；
- 根据追踪角度进行局部旋转；
- 执行二维码增强解码。

这可能造成：

- 模板制作时扫描失败，但使用生产处理方式可能成功；
- 模板制作时扫描成功，生产扩边后却受到周围字符干扰。

当前模板验证位置：

```text
widget.cpp:2989
```

建议模板验证和生产检测共用完全相同的处理入口，包括：

```text
相同padding
相同灰度处理
相同读码顺序
相同optionFlags
相同时间预算
```

不要长期维护两套相近但不完全相同的二维码处理规则。

### 4. 60 ms目前不是严格的硬超时

当前程序会在每次ZXing调用之前检查累计耗时，但DLL接口没有接收截止时间。

例如：

```text
调用前累计耗时55 ms
→ 进入一次ZXing调用
→ 该次调用执行80 ms
→ 实际二维码阶段可能达到135 ms
```

所以当前60 ms的实际含义是：

```text
超过预算后不再发起下一次尝试
```

它无法终止已经进入DLL的单次解码调用。

接口位置：

```text
BarcodeDecoderApi.h:42
```

如果现场要求二维码阶段严格不超过60 ms，需要扩展DLL接口，例如传入：

```cpp
int deadlineMs;
```

或者：

```cpp
int remainingTimeMs;
```

并在ZXing DLL内部约束搜索过程。仅在Qt主程序外层计时无法形成严格的硬截止。

### 5. 当前增强策略存在重复搜索

当前最多会尝试：

1. 原始快速路径；
2. 原始图增强模式；
3. 补静区；
4. CLAHE；
5. 中值滤波；
6. 自适应阈值；
7. 0.75倍缩放；
8. 1.5倍缩放。

增强路径通常同时启用：

```text
TRY_HARDER
TRY_ROTATE
TRY_INVERT
```

但追踪ROI已经根据姿态转正，绝大多数情况下没有必要让每一种增强图都重新进行旋转搜索；反色搜索也没有必要在每次尝试中开启。

当前策略位置：

```text
widget.cpp:2568
```

建议调整为：

```text
1. 原图，Data Matrix only
2. 当前Profile上次成功的专属策略
3. 补静区 + TRY_HARDER
4. CLAHE + TRY_HARDER
5. 中值滤波 + TRY_HARDER
6. 自适应阈值
7. 最后才使用TRY_INVERT
8. 极端情况下才使用TRY_ROTATE
```

这样不会删除现有兜底能力，但可以让正常产品更早结束读码。

另外，一次偶发失败不应该立即清空该Profile上次成功的策略。可以连续失败3～5次后再清空，避免后续正常产品重新执行全部策略。

### 6. 多Profile只选择最高追踪分，缺少歧义保护

当前程序会直接选择追踪分数最高的Profile。对于外观相似的Data Matrix，最高分和第二名可能非常接近。

由于当前二维码只判断“是否可读”，不校验二维码内容，因此可能出现：

```text
选择了错误Profile
→ 二维码仍然可读
→ 使用错误Profile的日期模板
→ 日期被判为NG
```

不需要改变“二维码只判断可读”的业务规则，但建议增加追踪置信度：

```cpp
top1Score >= profileMinScore
&& top1Score - top2Score >= ambiguityMargin
```

如果两个模板的追踪分数过于接近，可以直接报告“模板匹配不确定”，避免使用错误的日期模板。

当前追踪阈值相关代码可从以下位置检查：

```text
TrackingPoseMatcher.cpp:191
```

### 7. 工程中存在两套二维码增强实现

生产流程主要使用：

```cpp
Widget::decodeBarcodeRoi()
```

工程中同时还存在独立的：

```text
BarcodeDecoder.cpp:134
```

两边的增强顺序并不完全相同，容易造成：

- 模板制作和生产检测的结果不同；
- 修改其中一套逻辑时遗漏另一套；
- 后续维护时难以确定实际执行的是哪套逻辑。

建议最终保留一个统一入口：

```cpp
BarcodeDecoder::decode(...)
```

模板验证、生产检测和离线测试都调用同一实现。

### 8. 二维码和日期算法仍位于Widget业务链中

二维码连续解码失败时，程序可能在Widget调用链中执行多次图像预处理和DLL调用，容易造成界面短暂停顿。

后续建议将以下过程移动到检测Worker：

```text
二维码解码
日期字库匹配
综合判定
```

Widget只接收最终结果并更新界面。该调整不改变算法，只调整线程和代码职责。

## 四、界面上可以优化的地方

### 1. 将识别内容改成结构化状态

目前二维码内容、日期状态和失败原因主要显示在同一个普通文本区域中。建议固定显示：

```text
二维码：可读 / 不可读
日期：正确 / 错误 / 未执行
最终：OK / NG
```

颜色建议：

- 可读、正确、OK：绿色；
- 不可读、错误、NG：红色；
- 日期未执行：灰色。

二维码原始内容可以单独放在可选择、可复制的只读文本框中。

### 2. 主界面显示操作原因，技术原因写入日志

例如DLL缺失时，主界面显示：

```text
读码组件不可用，请联系设备维护人员
```

日志记录：

```text
BarcodeDecoder.dll load failed
GetLastError=...
DLL路径=...
```

这样既不会让工人面对内部技术信息，也能为维护人员保留完整故障信息。

### 3. 模板制作时显示程序实际扫描区域

框选成功后，建议预览：

- 实际映射到原图的二维码ROI；
- 解码器返回的四个角点；
- 扫描内容；
- 使用的增强策略；
- 本次扫描耗时。

这可以帮助发现：

- UI坐标映射偏差；
- 工人框入了日期区域；
- 二维码边缘被裁掉；
- padding过大；
- 实际扫描区域和界面框不一致。

不需要重新增加L形精定位，直接显示ZXing返回的角点即可。

### 4. 开始检测前显示Profile健康检查

建议显示类似：

```text
07247：正常
07248：二维码模板不可读
07249：缺少字符模板“7”
```

如果有任一Profile失败，就阻止启动检测，并明确提示需要修改的模板。

### 5. 高级二维码参数不要放到普通操作区

以下参数可以放在维护人员页面：

```text
ROI扩边比例
失败时间预算
是否启用增强
首选策略
追踪最低分
模板歧义阈值
```

日常工人界面保持简单，避免误修改检测参数。

## 五、建议实施顺序

建议按照以下顺序实施：

1. 检测启动前预检全部二维码Profile。
2. 统一模板制作和生产解码入口及ROI处理。
3. 优化ZXing尝试顺序，按策略分别启用`TRY_ROTATE`、`TRY_INVERT`和`TRY_HARDER`。
4. 增加多Profile追踪歧义保护。
5. 调整界面状态展示和模板预览。
6. 接入多相机或后台并发Worker时，再将日期检测改为明确返回单件结果，并统一最终输出。

## 六、最终结论

当前二维码+三期的算法顺序、短路逻辑以及OK/NG计数规则没有问题。

当前单相机同步运行时：

```text
OK数量 = totalImages - ngImages
```

能够正确统计，无需为了计数立即修改。

现阶段更值得优先处理的是：

- 旧模板和全部Profile启动前没有统一预检；
- 模板制作与生产ROI处理没有完全复用同一入口；
- 60 ms只是外层停止重试的预算，不是DLL内部硬超时；
- 增强策略存在重复旋转和反色搜索；
- 工程中存在两套二维码增强实现；
- 多Profile缺少追踪歧义保护。

这些问题的优先级高于继续堆叠新的图像增强或复杂几何定位算法。
